# Excercise 4


1. Why would we aim to detect success in results, instead of the more classical way of detecting errors/failures?


> Because there's always finite numbers of soltuons/succes states compared to infinite number of errror states. 


2. Why would we want to self-terminate, instead of handling the error immediately in the "primary" (as opposed to deferring it to the backup as it "spins up")?

> By terminating the program we ensure that any kind of error will be corrected, since we start at a clean slate/valid state (given we are not restarting from the error state). While trying to fix a infinite set of errors will create a much harder code. 


3. Is there any reason to prefer a process pair style, as opposed to making a separate supervisor-like program whose sole purpose is to restart the main program?

> Process pairs eliminate the single point of failure that a supervisor introduces.

4. Something to think about: Usually, a program crashes for a reason. Restoring the program to the same state as it died in may cause it to crash in exactly the same way, all over again. How would you prevent this from happening?

> If the program restarts from a given checkpoint, then it's also necessary to validate the checkpoint to prevent restoring from an invalid state. Or else we'll end up in an infinite loop.
